# 週次Codexの接続修正と検証

共有runnerは子CLIの環境変数を限定する。旧entryは削除されるTOKYO_WEEKLY変数を参照しており、呼び出し前にKeyErrorで止まった。各工程のentry.pyと隣接JSONで、実CLI・schema・応答先・工程・worktree・開始HEADを渡す方式へ変更した。Codexのモデル・権限、30件条件、独立レビュー、指定merge、公開照合は変えない。Claude収集の主モデルは現行のOpus 5.5に合わせ、主モデルを実メタデータで照合する。旧Fableのcaptured fixtureは保存し、モデルIDだけの意図した差分を合成検査で分類した。

I1: 最小環境でも実装・レビュー・公開の3工程を起動できる。I2: 不正binding、相対パス、別工程、出力先逸脱、HEAD不一致ではCLIを起動しない。I3: STOP・実行中lock・未確定stateでは再配置しない。I4: 接続失敗は候補0件や公開成功にしない。I5: 既存の接続configとstateを保持する。

テストは旧方式の失敗をRedで再現してから修正した。3工程の正常と21個の不正bindingを実コードで検査し、旧envへ戻す変種も失敗として検出する。未確定公開の再送禁止、30件未満、モデル不一致、レビュー不承認、二重lock、公開全行/安定IDの既存検査を維持する。有限の条件分岐と実ファイルを直接扱うためZ3/TLA+を増やしていない。端末全体や将来のプロバイダ稼働は保証しない。

実プロバイダでの確認は公開なしの専用スクラッチで行い、実ファイルI/O・別レビュー呼び出し・GitHub読み取り認証と応答schemaを確認する。本番週次の成功や実データの収集済みとは区別する。実行コピーは同じhash、同じlabel、金曜09:05 JST、RunAtLoad=falseを読み戻し、11/20の初回へ備える。

## 検証結果

Python 3.15.2で全24検査が成功した。接続修正後のコードで、実Opus収集schemaの診断とCodex実装・別レビュー・公開の3工程I/O診断が成功した。診断は専用の合成入力を使い、実装工程が実ファイルを書き、レビュー工程が同じhashを確認し、公開工程が既存GitHub認証でrepositoryとpush権限を読み戻した。実際の収集・commit・push・公開は診断から行っていない。

独立Codexは最小環境の3工程と不正binding・モデル不一致を読み取り専用で検証し、未解決のコード指摘なしとした。実行コピー・launchdの導入結果は端末の稼働記録へ残す。これらは将来の週次データの正しさや、Mac停止中の定刻起動を保証するものではない。

PRとmainでも同じ24検査を実行する。GitHub公式Actionは完全commit、Pythonは3.15.2へ固定し、権限はcontents:readだけとした。Pagesへの公開は既存のmain公開経路を使う。
